Lesson 01 Ticket 09 Open Blocked by 04, 13

Feeding the Graph Back

Recording every decision the agent makes costs nothing. Putting any of it back into the agent's head is where the whole feature is won or lost.

The winCapture is free. Consumption is the bill.

Everything settled so far in this project has been about writing things down. Ticket 03 established that Capture rides on events Pi already emits, and writes one SQLite row per assistant message. No second model runs. No extra tokens are spent. The store just accumulates.

Ticket 09 asks the opposite question. Given that store, how does any of it reach the agent again? Every answer costs context, and context is the scarcest thing the agent has. This is also the only place the feature can make the agent measurably worse, by handing it confident reasoning about code that was deleted three months ago.

By the end of this page you should be able to name the five decisions ticket 09 has to make, and point at the exact Pi hook each candidate answer would use.

Vocabulary Capture is the online pass that only witnesses. Assembly is the offline pass that derives judgements. Both are defined in packages/decision-graph/CONTEXT.md, which is binding on every part of this feature.

Question 1 of 5What does the agent actually receive?

Three shapes are on the table in the ticket: text injected into the system prompt, a tool the agent can call, or a summary produced at compaction time. Reading packages/coding-agent/src/core/extensions/types.ts turns those from abstractions into named hooks with known capabilities.

Shape What it would use What it costs Evidence
Prologue Return a replacement systemPrompt, or a message, from before_agent_start. Paid once per Run, then re-sent on every turn of that Run whether it was needed or not. BeforeAgentStartEventResult, types.ts:1102
Per-turn splice Return rewritten messages from the context event. Most surgical and most dangerous. It fires before every provider call and can rewrite history. ContextEventResult, types.ts:1065
Queryable tool A query_decisions tool registered by the extension. Nothing until called, minus the tool definition itself. But the agent has to decide to call it, and that costs a round trip. Tool registration, extensions.md
Post-compaction Re-inject after session_compact fires. Only paid when the agent has just forgotten something. See question 4. session_compact, extensions.md:388+

Worth flagging against ticket 03. That ticket dropped the fork of Pi's core for Capture, but kept a core edit pre-authorized for ticket 09 alone, in case injection needed an interception point the extension surface could not reach. On the evidence above, it does not. Two documented hooks already return mutated context, and a third fires at the compaction boundary. Ticket 09 can probably hand that pre-authorization back unused, which is a real result rather than a formality.

Cost note The prologue shape looks expensive but is the friendliest to prompt caching, because it sits at a stable position near the front of the context. The per-turn splice is the opposite: rewriting messages mid-history invalidates the cache behind the edit.

Question 2 of 5Which slice gets surfaced, and by what rule?

The store will be far larger than any context window, so something has to choose. The ticket adds one hard constraint: the rule must be deterministic. No model gets to pick, because a model picking is exactly the second inference pass this whole project refuses to pay for.

The candidates named are decisions touching files in this turn, the last N decisions, and decisions on the failing path. All three are cheap to compute. None of them is any good on its own, which is why ticket 09 is blocked by ticket 13.

Ticket 13 is the one that works out which decisions still explain the current state of a file, by checking whether a later edit provably overwrote the bytes an earlier one wrote. Its worked example is the whole argument: six months in, a.ts carries 200 decisions, and the rationale from March describes code rewritten in June. Feed all 200 back and the agent gets worse, not better. So ticket 13 supplies the relevance test, and ticket 09 only picks the window over it.

Question 3 of 5What is the budget, and what gets dropped first?

A hard token cap, plus an ordering for what falls off the end when the cap binds. The ticket asks for both and settles neither. The schema from ticket 04 already carries enough columns to sort by: how recent a decision is, whether ticket 13 marked it superseded, and what its WHY Source rung was.

That last one matters more than it looks. Ticket 02 established that no provider hands back raw chain of thought, so every Decision records where its rationale came from, on a five rung ladder from a provider summary down to nothing at all. A decision whose only WHY is the assistant's own prose is weaker evidence than one carrying a real reasoning summary, and the store knows which is which. Dropping by rung is available for free.

Measured, not guessed Ticket 04 sized real records rather than estimating: median 1.8 KB per Decision against 289 actual assistant messages. Budget arithmetic here has a real number behind it.

Question 4 of 5The interesting one: what about compaction?

Compaction is where the agent forgets. When context approaches the window, prepareCompaction picks a cut point in the session, sends everything before it to a model to be summarized, and keeps a recent tail verbatim.

Now put the graph next to that picture. The store holds the same history, verbatim, never summarized, plus a record of which parts are still live. So the ticket's sharpest question is whether the graph should be a replacement for what compaction discards, re-injected right after a compaction event, or an independent channel that ignores compaction entirely.

There is a clean argument for the replacement reading. Compaction's summary is written by a model, which is inference. The graph's WHY is read from what the model already said, which is testimony, and it arrives stamped with its own provenance. Those are different in kind, and the graph is the one that can prove where its content came from.

There is an equally clean argument for the risk. Compaction exists to shrink context. Anything re-injected straight afterwards counts against the window that was just cleared, and Pi re-checks whether to compact on the same token threshold. Get the budget wrong and the graph pushes context back over the line that triggered compaction in the first place. The ticket calls this the most likely place to break something, and that is the mechanism.

Already paid for Ticket 03 subscribed Capture to session_before_compact and session_compact before anything needed them, so compaction boundaries are already being stamped into the store. Cheap then, unrecoverable later.
Correction to the ticket Ticket 09 points at packages/agent/src/harness/compaction/. That copy is only re-exported from the agent package's public index and exercised by its own tests. The coding agent runs a second, near-identical copy at packages/coding-agent/src/core/compaction/, which is what agent-session.ts:66 imports. Read that one.

Question 5 of 5Should consumption default to off?

The ticket makes the case in a single parenthesis, and it holds up. A build that only captures is still worth shipping: its overhead can be measured, and a human can read the graph through the viewer without the agent's context ever being touched.

Defaulting off also protects the experiment. Ticket 11 has to compare a graph-off arm against a graph-on arm, and it names the confound directly: injecting anything at all changes behaviour, regardless of whether the content was useful. If consumption is a flag rather than a default, the control arm is the ordinary product rather than a special build made for the benchmark.
